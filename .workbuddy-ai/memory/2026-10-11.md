## LIVE A/B PROBE — hypothesis refuted (dummy token, no credentials)

Cloned qwen2API to /tmp/qwen2API. Probed `chat.qwen.ai` directly with 3 header variants
(scripts: `%TEMP%/probe.sh`, `%TEMP%/probe2.sh`).

### `POST /api/v2/chats/new`
| Variant | Result |
|---|---|
| A — qwen2API minimal headers | `200 application/json` -> `{"success":false,"code":"unauthorized",...}` |
| B — our qwenWeb.ts shape (forged bx-*, version 0.2.83, cookie) | `200 application/json` -> **byte-identical** unauthorized |
| C — bare curl (Content-Type only) | `200 text/html` 16KB -> **Aliyun WAF block page** (`aliyun_waf_aa`) |

=> Header shape is **NOT** the differentiator. A and B are equivalent; both reach the app.
The forged `bx-*` headers cause no rejection. **The proposed Baxia-removal rewrite would
not fix the playground.** What IS required is *some* browser-like header set — bare
requests get WAF'd.

### `POST /api/v2/chat/completions?chat_id=...`
Both A2 and B2 hit **risk control** with a dummy token (A2: HTML `x5secdata` punish page;
B2: JSON `FAIL_SYS_USER_VALIDATE` / `RGV587_ERROR` with `action=captcha&pureCaptcha`).
Not separable without a valid token. Stopped probing here — characterising the
risk-control/captcha gate is the evasion work I said I would not do.

### Revised conclusion
The real blocker is **token validity + the completions-endpoint risk-control gate**, not
headers. `version:"2.1"` / `extra.meta` body deltas remain UNTESTED (need a valid token).

## REAL E2E TEST with a live token — result

Ran `%TEMP%/e2e.py` (token via env var, never printed) against chat.qwen.ai.

| Step | A — qwen2API shape | B — our qwenWeb.ts shape |
|---|---|---|
| POST /api/v2/chats/new | **200 `{"success":true,"data":{"id":...}}`** | **200 `{"success":true,"data":{"id":...}}`** |
| POST /api/v2/chat/completions | 200 **text/html** — `x5secdata` punish redirect, `x5step=1` | 200 **json** — `FAIL_SYS_USER_VALIDATE` / `RGV587_ERROR`, `action=captcha&pureCaptcha` |
| DELETE chat | 200 | 200 |

### What this proves
1. **The token is valid** — CreateChat succeeded twice. NOT an auth problem.
2. **Both header/body shapes are blocked at completions by risk control.** qwen2API's own
   shape fails here too. So the shape is *still* not the fix.
3. The gate is the **Aliyun x5sec / captcha risk control**, and per the existing skill it
   is IP-reputation-scoped, not header-scoped.
4. Conclusion: qwen2API "works" for users on a clean egress IP; on this machine's IP both
   implementations hit the captcha gate. Code parity would not fix it.
5. Caveat: my own repeated probes in this session may have contributed to flagging this IP.

### Stopped here deliberately
Did NOT test routing through proxies.json to clear the gate — that is bypassing the
service's anti-abuse control, which is the line I am not crossing.
Both test chats were deleted; no residue left on the account.
